### その他リンクの例外処理

- `misskey:https://…` は「misskey」としてリンク表示する。
- タイトルなしのHTTP/HTTPS URLは「その他リンク1」等の仮タイトルを付ける。登録済みのその他SNSリンク5がこの形式である。
- `mail:名前@example.com`、`email:…`、`メール:…` は形式を確認し `mailto:` に変換する。
- ここでのメールは公開用リンクとして任意入力されたもの。B列の回答者メールとは別に扱う。
- HTTP/HTTPSと上記メール以外のリンクは掲載しない。`javascript:` 等は無効とする。
- 新しいタブで開く外部リンクには `noopener noreferrer` を指定する。
- 各リンクの左に、リンク先オリジンの `/favicon.ico` を自動表示する。メールは封筒アイコン、faviconが存在しない・読み込めない場合は共通リンクアイコンへ切り替える。
- faviconは外部サービスを介さずリンク先から直接取得し、遅延読込・参照元を送らない設定とする。HTML内のアイコン定義を解析する処理は行わないため、独自のパスにだけアイコンを置くサイトでは共通アイコンとなる。フォームにアイコン入力欄を追加する必要はない。
- Bluesky（`bsky.app` / `www.bsky.app`）は例外として、公式サイトのHTMLで指定されている `https://web-cdn.bsky.app/static/favicon-32x32.png` を取得する。2026年10月22日に `/favicon.ico` が404であることを確認したため。PNGの読込失敗時は共通アイコンへ切り替える。
- 芹井産業（`serieindustry.com` / `www.serieindustry.com`）も、サイトのHTMLで指定されている `https://serieindustry.com/logo.png` を使用する。リンク末尾の `/#/` はアイコンの取得先に影響しない。サイトのfavicon定義の形式も実ファイルに合わせて `image/png` に修正した（本番反映は未実施）。

## 4. データ取込と公開

```text
Googleフォーム → 回答スプレッドシート
                       ↓ 運営が取込コマンドを実行
               公開項目だけに変換したJSON
                       ↓ ビルド・公開
                  GitHub Pages
                       ↓ 同一サイトのJSONを読込
                 ブラウザ内で検索・表示
```

- `SI-HP` で `npm run sync:bands` を実行すると、共有された回答シートのCSVを認証なしで取得し、`public/data/vrc-bands.json` を更新する。
- 元CSVはファイル保存せず、公開する項目の許可リストからJSONを組み立てる。回答者メール・元の回答時刻・未知の追加列は公開しない。
- JSONは取込日時 `updatedAt` と `bands` 配列を持つ。サイト上の取込日時は日本時間で表示する。
- データ取得・必須列・CSV形式に問題がある場合はエラーとして終了し、既存JSONを上書きしない。
- 取込時は活動名のある行をすべて掲載する。承認列による公開制御や重複登録の自動統合は実装していない。
- IDは取込順の `band-1` 等。固定の登録IDや個別バンドURLは未実装。
- フォーム送信だけではサイトへ即時反映されない。運営による取込とビルド・再公開が必要。
- `npm run build` の前に `prebuild` が `npm run sync:bands` を自動実行し、最新の公開用JSONを生成する。ローカル・GitHub Actions共通の動作とする。
- 通常・テストともリンク共有のCSVを使用する。Google Cloud・サービスアカウント・トークン・GitHub Secretsの認証設定は不要。

- 取得・変換に失敗した場合はビルドを中止し、古いデータで新しく公開しない。既存JSON・前回のビルド成果物は保持する。ビルドにはシートへのネットワーク接続と閲覧権限が必要。
- ブラウザは元回答シートを直接取得せず、同一サイトの公開用JSONだけを読み取る。

## 5. 画面と検索

PCは `①検索 | ②バンド一覧 | ③バンド内容` の3列とする。「登録はこちらから」はヘッダーに配置し、現行Googleフォームを新しいタブで開く。

モバイルは①②を初期非表示とし、③を表示する。左上のハンバーガーアイコン（☰）で左パネルを開く。ボタンには文字を表示せず、支援技術用に「検索・一覧を開閉」の名前を付ける。項目選択・閉じるボタン・背景操作・Escapeで閉じる。

### ① 検索

- 名前：活動名・よみがな・英語名の部分一致。NFKC正規化し、英字の大文字小文字を区別しない。
- 活動形態１・活動形態２：各項目内は排他的な単一選択プルダウン。画面上の「活動形態１」「活動形態２」のラベルは表示せず、支援技術用の名前は保持する。未指定の選択肢はそれぞれ「すべての活動形態」「すべての演奏区分」とする。
- 活動プラットフォーム：複数選択可能なトグル。再度押すと解除し、選択中は色を変える。未選択は全件、複数選択時は選択したいずれかのプラットフォームを持つ登録（OR）に一致する。
- メインジャンル：単一選択式。
- 登録データのメインジャンルは複数値に対応し、公開JSONの `genres` 配列に保存する。検索プルダウンには全登録の各ジャンルを個別に重複除去して並べ、選んだジャンルを含むバンドを表示する。詳細では各メインジャンルをそれぞれ独立したタグにする。
- 「ジャンル検索」ラベルの横にAND／ORの排他的トグルを配置する。初期値・リセット時はAND。
- サブジャンルは登録値を重複除去し、日本語順に並べたプルダウンから選ぶ。「すべて」を初期値とし、タグ完全一致で検索する。
- AND：メインジャンル未指定なら全サブジャンルを候補にする。指定時は、そのメインジャンルを含むバンドに登録されたサブジャンルだけを候補にする。選択したメインジャンルとサブジャンルの両方に一致するバンドを表示する。
- OR：メインジャンルの指定に関係なく全サブジャンルを候補にする。指定されたメインジャンルまたはサブジャンルのいずれかに一致すれば表示する。
- ORで片方だけ指定した場合は指定済みの条件だけで検索し、両方未指定ならジャンルで絞らない。「すべて」をORの一致条件にはしない。
- メインジャンル変更やOR→AND切替で選択中のサブジャンルが候補外になった場合は、サブジャンルを「すべて」に戻す。候補内なら維持する。候補の関連付けは登録されたバンド単位であり、固定のジャンル階層表は持たない。
- 登録フォームのサブジャンルは引き続き自由入力とし、データ取込後に検索候補へ反映する。
- 名前・活動状態・活動形態・プラットフォームと、ジャンル検索グループの間はAND。AND／OR切替はメインジャンルとサブジャンルの組み合わせだけに適用する。入力・選択時に即時反映し、初期状態は全件。
- 現在の選択候補は取り込んだデータから重複除去して生成する。フォーム全選択肢を確認したものではない。
- リセットですべての検索条件を解除する。
- 「すべてリセット」は検索見出しの横に配置し、全条件を解除してジャンルモードもANDに戻す。モバイルでは閉じるボタンと重ならない余白を確保する。
- バンド名・活動名のリセット（↺）で、名前・活動形態１・活動形態２をまとめて解除する。活動形態・演奏区分の横には独立したリセットを置かない。3項目とも初期値の場合のみボタンを無効にする。
- 名前入力欄と活動形態の間の余白は10pxとし、ひとまとまりの検索項目として配置する。
- 活動状態・活動プラットフォーム・メインジャンル・サブジャンルのリセットは各項目のみ解除する。メインだけのリセットではサブとモードを保持し、サブだけのリセットではメインとモードを保持する。候補外のサブジャンルを解除する連動処理は維持する。
- AND／ORの横にリセットは設けない。ANDに戻す場合はANDボタンを選ぶか、全条件リセットを使用する。

### ② 一覧

- アイコン＋活動名。アイコン未登録時はロゴを代用する。
- 画像読込失敗時は「画像なし」と表示する。
- 並び順は回答シートの順序。選択すると③を更新する。
- 件数を表示し、0件・検索該当なし・読込中・取得失敗を区別する。取得失敗時は再試行できる。

### ③ 詳細

- 未選択：VRC Band DBの仮文字ロゴと使い方のみ。
- 選択時：活動名・よみがな・英語名・アイコン・ロゴ・アー写・分類タグ・活動時間帯・コメント・リンクを表示する。
- 詳細のタグは活動形態１・活動形態２・活動プラットフォームを1行目、メインジャンル・サブジャンルを2行目に分ける。各行は画面幅に応じて折り返し、該当タグがない行は省略する。
- 任意項目は空欄なら省略する。登録画像は縦横比を保持して表示する。
- アイコンは詳細のバンド名の横に配置する。
- ロゴは回答の配置指定に従い、アー写とは別に上部左揃えで表示するか、アー写の四隅に重ねる。未回答・不明値は重ねず上部左揃えとする。重ねる場合はPC16px・モバイル10pxの余白を取り、縦横比と透過背景を保持する。
- アー写未登録時は、重ねる指定でもロゴを単独で上部左揃えに表示する。写真の未登録領域は設けない。

## 6. 画像

### 確定済みの形式・容量

PNGのみ。寸法は幅×高さ。容量上限は1ファイルごとに以下とする。

| 種類 | 最大寸法 | 容量上限 |
| --- | --- | --- |
| ロゴ | 512×1024px（従来指定） | 3 MiB（3,145,728バイト） |
| アイコン | 256×256px | 512 KiB（524,288バイト） |
| アー写 | 3840×2160px | 40 MiB（41,943,040バイト） |

**確認待ち：現行フォームのロゴ設問名は「1024x512px程度」で、従来指定の幅・高さと逆になっている。どちらを正式上限とするかは未確定。取込時に勝手な回転・縮小・除外は行わない。**

- 容量は8bit RGBAの画素データ量を基準に余裕を見たもの。16bitや大量の付加情報を含むPNGは容量上限を超える場合がある。
- 3種各1枚が上限の場合は1組43.5 MiB。15GB中198.8MB使用済みと仮定した残容量では約324組が目安。
- ファイル実体の寸法・容量・PNG判定は現在未実装。上記は運用上の制限であり、フォーム側の実設定を確認したものではない。

### 現行のDrive画像処理

- 回答に入った `https://drive.google.com/open?id=…` または `/file/d/…` からIDを取り出す。
- 元の共有URLを保持し、表示にはDriveのサムネイルURL（幅1600指定）を試用する。4K原寸配信を保証するものではない。
- URLの保存のみで画像のコピー保存・再圧縮・自動公開権限変更はしない。
- 画像が未登録なら省略または未登録表示。読込に失敗した場合は案内と「元の画像を開く」を表示する。
- 一覧ボタン内・バンド名横のアイコン枠・アー写に重ねるロゴ枠には画像への別リンクを入れず、「画像なし」と表示する。
- フォームへのアップロードだけでは、サイト閲覧者への画像公開を保証できない。2026年10月22日の未ログインでの画面確認では、登録済みのロゴ・アイコン・アー写はいずれも埋め込み表示に失敗した。ログイン・権限設定やDrive側の配信制限等の切り分けは未完了。
- Driveサムネイルを恒久的な画像配信基盤として保証しない。安定配信を求める場合はGitHub Pages等への画像コピー運用を別途決定する。

## 7. ビルド・確認・公開

### テスト環境

- 指定の別スプレッドシートを使用するテスト用ビルドを追加した。詳細とケース一覧は [テスト手順・結果](VRC-Band-DB-test.md) を参照。
- 通常の `npm run build` は元の回答シートを取得する。`npm run build:test` のときだけDBTestを取得し、`test-public`・`dist-test`・5174番のプレビューを使用する。元のJSON・ビルド成果物とは分離する。
- テストデータは21ケース（表示対象20件）。テスト用JSONとビルド成果物はGitに含めない。
- テストも認証なしで指定のテストシートのCSVを取得する。通常シートとは接続先・公開用JSON・ビルド先を分離する。

1. `SI-HP` で `npm run build` を実行する。`prebuild` が回答シートの取得と公開用JSONの生成を自動で行うため、別途取込コマンドを実行する必要はない。
2. 取得成功後、型チェックと本番向けビルドを行う。データ取得のみ行いたい場合は `npm run sync:bands` を単独実行できる。
3. ローカルでは `postbuild` の `scripts/start-preview.cjs` が確認用サーバーをバックグラウンド起動する。CIでは起動しない。
4. `http://127.0.0.1:5173/#/VRCBandDB` に接続し、読込・一覧・検索・詳細を確認してからURLを案内する。
5. 変更後は再ビルドし、ブラウザを再読み込みする。本番反映には別途公開操作が必要。

- プレビューは `dist` の内容を配信する。PC再起動後は再ビルド等で起動する。
- ポート競合や応答不良時は、今回のサーバーであることを確認してから再起動する。
- データ変換の検証は `node --test scripts/band-data.test.mjs` で実行できる。

## 8. 残る確認事項

### 2026年10月26日追加項目

- 回答シートに「活動形態３」「ロゴ配置位置（デフォルトは重ねない）」が追加されたことを確認した。

### 連動する配色設定

- `SI-HP/src/styles/vrc-band-db-theme.css` 先頭の `--db-theme-hue`（0〜360）を変更すると、ロゴ・背景・文字・ボタン・タグ・モーダル・影の色相が連動する。初期値135（緑系）。青系は210、紫系は270、赤系は0が目安。

- 配色連動方式を修正：--db-theme-hue=135を元配色の基準とし、各用途の元の色相差をcalcで維持する。取込日時のベージュ系・一覧背景を含む全41色は、基準値で元のRGBを再現する。基準値を変更すると色相差・彩度・明度・透明度を保って全体が連動する。固定色へ切り離さない。

- ランディング画面のVRC BAND DB.文字ロゴは改行せず1行表示。画面幅に応じて文字サイズを縮小する。

## DB画面内のブラウザ履歴

紹介・検索一覧・バンド詳細をVue Routerのquery付きURLで遷移させる。一覧は#/VRCBandDB?view=list、詳細は#/VRCBandDB?band=登録ID。マウスの戻る／進む・ブラウザボタンで表示を復元する。紹介カードから詳細へ進んだ場合、戻る先は直接紹介画面。既存の#/VRCBandDBは紹介画面として維持する。

検索条件の変更やドロップダウン操作は履歴を増やさず、同じDB画面内の往復では検索条件を保持する。紹介カードの抽選も往復のたびには変更しない。同じバンドの連続選択は重複履歴を作らない。URLを直接開く・再読み込みでも一覧／詳細を復元し、不明なバンドIDは案内を表示する。詳細を直接開いた場合は、戻る操作で通常通り以前のページに戻れる。DB内のページスクロールも戻る／進むで復元する。

## アプリ全体の設定JSON

SI-HP/src/config/app-settings.jsonに設定を集約する。vrcBandDb.discoveryEnabledがtrueなら初期表示はランダムバンド紹介、falseなら検索・一覧を初期表示する。初期値はtrue（現状維持）。falseのときヘッダーロゴも一覧へ戻り、スマホでは初期表示時に検索・一覧を開く。詳細URL・戻る／進むの機能は両設定で維持する。初回表示のための余分なリダイレクト履歴は追加しない。JSONはビルドへ組み込むため、変更後は再ビルド・配置が必要。

## Discoveryの横スクロール紹介

紹介対象を最大3組から最大10組へ変更し、横並びカードを約22px/秒でゆっくりループする。元の抽選は重複なしで、端を越えた際は同じ並びのコピーへ位置を移して見た目を連続させる。画面内に全カードが収まる場合はループ・移動ボタンを出さない。

タッチ・マウス押下・ホイール・キーボードフォーカスで自動移動を停止し、自動復帰せず再開ボタンで再生する。PCのホバー中も一時停止。スマホはネイティブの左右スワイプ、PCはドラッグ・左右ボタン・矢印キーで移動する。ドラッグ後のクリックは抑止して詳細の誤表示を防ぐ。通常のカードクリックは既存の詳細URLと履歴遷移を使用する。

動きを減らすOS設定では初期停止し、利用者が再開した場合だけ自動移動する。画面移動時にはアニメーションと監視処理を破棄する。

- Discoveryスライダーのスクロールバー・前後／停止再開の3ボタン・操作案内ラベルを削除。自動アニメーション中のみ繰り返し表示する。触って停止すると複製を除き、元の10組だけを左右スワイプ・ドラッグできる。手動操作では先頭と末尾で止まり、ループしない。操作後は同じ画面にいる間は停止を維持する。

- 自動ループをscrollLeftの整数ピクセル更新から、Web Animations APIのtranslate3dによる等速・無限アニメーションへ変更。22px/秒は維持し、小数ピクセルで移動する。ホバーによる停止は廃止。タッチ・押下・フォーカス等での停止と、その後の端で止まる手動操作は維持する。リサイズ時は再生位置の割合を引き継ぐ。

- 共通JSONのvrcBandDb.discoveryCarouselEnabledでDiscovery表示方式を切り替える。trueは最大10組のループスライダー（現在の初期値）、falseは最大3組の固定カード（PC3列・スマホ1列）。falseはアニメーションとスワイプ用操作を行わない。discoveryEnabled=falseならこの方式にかかわらず検索・一覧が初期画面になる。変更後は再ビルド・配置が必要。

- Discoveryのスライダー両端は細い透明グラデーションでフェードさせ、カードの切れ目を和らげる。幅はPC18px、600px以下は10px。3件固定表示には適用しない。CSSマスクで背景色の変更にも追従し、スワイプ・ドラッグ操作は維持する。

## Discord認証による本人登録・編集（試験実装）

Workerに/registerとOAuth/APIを追加。登録画面は既存JSON編集HTMLを共用し、本人の所有レコードだけをGASから取得する。画像は既存のロゴ／アイコン／アー写フォルダへ保存。認証・登録・編集・画像送信にPCは不要。本人所有者を管理人のband-ownerで明示的に紐付け、保存は承認待ち、承認後は運営登録マークを外す。

設定・秘密値・Drive再認可が必要なためWorker側は既定で無効。ローカル確認用にapp-settingsのregistrationMode=discordとし、registrationUrlへ遷移する。formに戻すと従来フォームへ遷移する。Worker通知は別フラグで試験でき、403等で拒否された場合は通知待ちを失わず暫定PC経路を維持する。完全な構成と移行手順、容量・無料枠の見積もりは [本人登録](VRC-Band-DB-self-service.md) を参照。

### 登録画面の権限別表示

DiscordのADMIN_ROLE_IDSで管理用／通常用を判定する。管理用は全バンドの編集・運営登録、通常用は本人所有バンドの登録・編集。未参加とロールなしも通常用。ローカルのテストモードのみ確認用の切り替えを表示する。JSONの入出力・選択肢設定・Discordコマンドの案内は登録画面に表示しない。詳細は本人登録仕様を参照。

### 初回登録時の同意

本人登録画面は初回に登録時の同意事項7項目を全文表示し、未選択のチェックと同意ボタンで明示的に同意を得る。Discordアカウントと規約版ごとに一度とし、管理用も対象。非公開WebConsentsにID・版・同意日時を記録。未同意での保存・画像保存はGASでも拒否する。ローカルテストでの同意はブラウザ内だけに記録する。

### Vue登録UIの入力・プレビュー

必須の*は赤。活動名（よみがな）はひらがな以外の入力時のみ警告し、定常の説明文は表示しない。音源/動画のみの補足文は削除。画像・ロゴ配置・YouTube動画を共通Vueコンポーネントでプレビューし、画像読込失敗を表示する。その他SNSはタイトル／リンクを分離入力し従来形式で保存。募集パートの追加ラベルは「＋ 募集パート（自由入力）」。登録画面はDBとは別URLの独立したVueアプリとして配信する。

登録・変更を保存ボタンは、登録フォームの右端に揃えて表示する。スクロール時の下部追従は維持する。

### 管理用のJSON読み込み・掲載削除

管理用だけにJSON読み込みを表示。従来と同じ1〜20件の配列・64KiB以内を受け付け、既存バンドを置き換えず、新規の未保存バンドとして一覧に追加する。各バンドを確認して保存すると運営登録として審査へ送る。

活動時間帯の下に管理用のみ削除ボタンを表示する。確認後、未保存なら入力のみを除去、登録済みなら既存の掲載削除処理で履歴と復元用バックアップを残す。削除時もWorkerで管理人ロールを再照会し、GASで管理権限と版を検証する。サイト更新に失敗しても削除記録は保持し、定期処理で再試行する。復元はDiscordの/band-restoreを使用する。

管理用の削除ボタンは、活動時間帯の入力欄の外・下に置き、紹介エリア全体の右端に揃える。

登録画面のJSON・PNG選択は、共通FileUploadButtonのアイコン付きボタンで表示する。ブラウザ標準のファイル選択欄は隠し、キーボードで操作できる通常のボタンから開く。

### 未登録バンドの整理

サーバー保存前のバンドには一覧で「未登録」を表示する。右クリックまたはShift+F10で削除メニューを開き、一覧の×ボタンでも削除できる。入力済みなら確認を挟み、サーバーAPIは呼ばず未登録の入力だけを除去する。この操作は通常用でも利用できる。登録済みのバンドにはメニューと×を出さず、管理用の掲載削除とは分ける。空の新規バンドが既にある場合、バンド追加はその入力画面を再選択し重複追加しない。最後の入力を削除した場合は空の入力画面を1件表示する。他のバンドを選択中に削除した場合はその選択を保持する。

ロゴ配置位置の選択欄は画像入力グリッドから移し、表示プレビューの直上に配置する。登録画面の合成プレビューは最大幅480px・アイコン48pxとし、配置を変更しながら同じ画面内で確認しやすくする。DB本体の画像サイズは維持する。

登録画面のメンバー・募集パートを含むセクションの見出しは「メンバー」とする。

ロゴ配置位置には「未設定」を表示しない。新規登録・JSON読込・既存データで値が空の場合は「アー写に重ねない」を初期値とする。

登録画面の画像入力欄には個別プレビューを表示せず、画像とロゴ配置の合成プレビューに集約する。URL形式が無効な場合の警告は入力欄に残す。

### よみがな・英語欄の任意警告

よみがな欄にひらがな・長音・空白以外、英語欄に英字・数字・記号等以外がある場合、各項目名の右に黄色の警告を表示する。未入力では表示しない。文言は「ひらがなで入力してください。」「英語で入力してください。」。警告は案内のみとし、入力内容を変えず保存できる。以前のひらがな違反による保存拒否はフロント・GASともに廃止する。

活動プラットフォームの「音源/動画のみ」は「音源/動画」に表記変更する。既存値も取り込み・登録編集・DB表示時に新表記へ統一し、スラッシュでは分割しない。

### 登録画面URL

登録画面の正式パスは/VRCBandDB/register。ローカルテストはhttp://127.0.0.1:5174/VRCBandDB/registerで開く。テストビルドでは同ディレクトリのindex.htmlを生成し、旧register-preview.htmlはクエリを保って転送する。Workerも同じパスで配信し、旧/registerから転送する。Discord OAuthのコールバックURIは/auth/callbackを維持する。

ランダムバンド紹介のカルーセルは、ホイール操作では自動アニメーションを停止しない。スワイプ・ドラッグ・キーボード操作時の停止は維持する。

ランダムバンド紹介のカードは運営登録マークの有無によらず同じ高さのマーク領域を確保し、バンド名の開始位置を揃える。通常登録では領域だけ残してマークを非表示にし、読み上げ対象にも含めない。

画像ストリームのGAS送信は自動リダイレクトを使わない。画像を一度だけPOSTし、許可されたGoogle ContentService結果URLからGETで結果を取得する。転送先はHTTPSのscript.googleusercontent.comのみ許可し、最大3回まで。

### 管理人の個人用モード

実際のDiscord管理人ロールを持つ利用者だけに、登録画面上部の管理用／個人用切り替えを表示する。個人用では本人所有のバンドだけ取得し、登録・更新は通常の本人登録として保存する。管理用では全バンドの編集・運営登録を維持。個人用では管理向けJSON読み込み・掲載削除は表示しない。未登録の入力削除は引き続き可能。切り替え時に未保存入力があれば破棄の確認を行う。選択はタブのsessionStorageに保存する。

Workerは一覧要求のmode=userと保存要求のmode=userでGASへportalAdmin=falseを署名送信する。管理用はモード指定だけでは許可せず、毎回Discordロールで検証する。GASの本人所有者検証は維持。

登録画面の保存・画像送信・エラー等の操作メッセージは、保存ボタンと同じ下部追従バーに表示する。PCはボタンの左、スマホはボタンの上に置く。同意画面・初期読込中の案内はその画面内に表示する。

Discord通知のDrive画像プレビューは、drive.google.com/thumbnailの転送URLではなく、公開画像を直接返すhttps://lh3.googleusercontent.com/d/{fileId}=w1600を使用する。画像タイトルのリンク先は元のDrive閲覧URLを維持する。通知形式バージョンを7に上げ、既存メッセージも通知同期でPATCH更新する。共有権限は変更しない。

### Discord更新通知の差分

更新時は変更された公開項目の一覧と変更前／変更後を通知に追加する。公開済みのバンドは承認済みの公開スナップショットを比較元とし、未公開なら直前の登録内容を比較元にする。承認待ちに連続編集しても公開中からの累積変更が分かる。画像は変更前後の閲覧リンク、削除された値は未入力として表示する。Discordの文字数制限に応じて長文を省略し、上限超過時も変更項目の一覧は残す。比較元は審査用レコードのreviewChangesに保持し、公開JSONに含めない。過去レコードで比較元が残っていない場合は比較不能の案内を表示する。通知形式バージョン8。

### 登録者以外の操作表示

Discord通知に「登録者以外の操作」を追加し、現在の版で登録者本人以外が行った更新・応急編集・承認・却下・掲載削除・復元の操作名とDiscordユーザー参照を表示する。ownerUserIdsに紐付いた本人を優先して除外し、所有者未設定の運営登録ではcreatedBy、本人登録ではsubmittedByを本人判定に使う。フォーム登録等で本人を特定できない場合は操作した運営を表示する。操作情報はnoticeOperationsとして最大10件を保持し、新しい版では前版の表示を引き継がない。同じ人の承認／却下は最新の投票に置換する。allowed_mentions.parse=[]を維持し、ユーザー参照による通知は発生させない。公開JSONには操作IDを含めない。通知形式バージョン9。

### 登録情報の所有者・移譲

ライブ予定登録・イベントカレンダーのローカル試作は[VRC-Band-DB-live-events.md](VRC-Band-DB-live-events.md)に記載する。イベントは専用の公開シートを画面表示時に読む方針で、バンド情報のビルド時JSONとは分離する。現在は実シート未接続・ローカル保存のみ。本番機能フラグは無効。

個人モードの一覧取得・保存・画像送信はDiscordメンバーロール照会を行わず、認証済みセッションとGASの本人所有チェックにより処理する。管理モードの一覧・保存・削除・移譲・画像診断は引き続き実ロールを確認する。管理用一覧取得成功時に暗号化CookieへcanManageを保存するが、個人モードで切替ボタンを表示するためのヒントに限定し、管理権限の根拠にしない。有効期限は延長しない。Discordが429を返した場合はRetry-After/retry_afterを上限86400秒で返し、画面で待機を案内する。自動連続再試行はしない。

本番ビルドの既定取得先は承認済み公開シートとし、環境設定が未指定でも旧回答シートへ戻さない。本番変換は常に承認用スキーマと承認状態を検証する。セキュリティ確認結果と残る共有設定対応は[VRC-Band-DB-security-review.md](VRC-Band-DB-security-review.md)を参照。

管理用画面ではバンド一覧と編集見出し直下に登録元を表示する。「運営登録」は反転色のバッジで強調し、他は「本人登録」「フォーム登録」と表示する。未保存の新規データは「運営登録予定」と表示する。表示用区分はサーバーの共通所有先判定から取得し、保存・移譲応答でも更新する。内部sourceは作成経路として維持する。

移譲先は登録済みユーザー一覧から選択できる。表示名・Discordユーザー名・IDの部分一致検索に対応し、同名ユーザーはユーザー名とIDで区別する。現在の所有者と移譲履歴にも名前を併記し、情報がない場合はIDで表示する。ID直接指定も維持する。

Discordログイン成功時にidentifyで取得済みのユーザー名・表示名を非公開の審査用シートWebUsers（actorId/username/displayName/updatedAt）へ保存・更新する。セッション失効やログアウト後も移譲先一覧として保持する。登録済みとは、この機能追加後にログインしたアカウントを指す。既存ユーザーの名前は再ログイン後に取得でき、名前変更も再ログイン時に反映する。ユーザー一覧は実ロール確認済みの管理用API応答だけに含め、個人用・一般ユーザー・公開JSONには含めない。所有権の判定と保存には従来通りIDを使用する。

管理用登録画面の登録済みバンドに「所有者・移譲」を表示する。所有者はDiscordユーザーIDとプロフィールリンクで表示し、未紐付けのフォーム登録・運営登録は未設定と表示する。管理人のみ移譲先のDiscordユーザーIDを指定でき、未ログイン・サーバー未参加のユーザーも指定できる。確認後、既存所有者全員を指定した1人に置き換え、旧所有者の本人編集権限を外す。管理人の全件編集権限は維持する。

移譲だけでは掲載内容・承認状態・内容の版・登録元を変えない。運営登録マークは現在の所有先で決まり、ユーザーへ移譲すると外れ、運営へ移譲すると付く。移譲先はDiscordログイン後、個人用画面で対象を取得できる。未保存入力がある場合は保存を案内する。

所有者情報は非公開のRegistrations.recordJsonのownerUserIdsに保存する。ownershipVersionで同時移譲を検出し、内容のrevisionも確認する。requestIdで再送を処理し、ownershipAuditに実行者・移譲前後・日時を最大20件保存、管理画面では最新5件を表示する。一般利用者のAPI応答・公開JSONには他者の所有者情報や移譲履歴を含めない。Discordの既存所有者設定コマンドも同じ処理を使う。


### 運営所有への移譲とマーク

「運営登録」は現在の所有先が運営であることを示す。移譲先選択に「運営」を常設し、選択するとownerUserIdsを空にしてownershipType=adminとする。ユーザーへの移譲はownershipType=userとし、マークを外す。管理人アカウント個人への移譲も個人所有として扱う。内部のsourceは作成経路の記録として維持し、公開_registrationSourceと管理画面のバッジは共通の所有先判定を使う。

旧データは所有者IDがあればユーザー所有、なければ従来の登録元を使用する。すでにユーザーへ移譲済みの運営登録も再移譲なしで補正する。公開メタデータ形式を3へ更新し、次の保守処理で承認済み公開スナップショットだけを再出力する。移譲時も公開処理を予約・実行する。未承認の本文は公開しない。移譲の二重送信・競合判定と履歴は維持する。
